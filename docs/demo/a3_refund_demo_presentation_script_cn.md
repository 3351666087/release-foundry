# ReleaseFoundry 电商退款 Demo 详细汇报讲稿

> 适用对象：第一次讲 Agent Evaluation 的学生
>
> 建议时长：10 至 12 分钟
>
> 演示数据：固定失败案例 + Docker 本地模型动态案例；两者都不连接真实订单，不执行真实退款

## 一、汇报前必须记住的三句话

1. A1 负责记录“Agent 实际做了什么”。
2. A2 负责判断“Agent 做得对不对”。
3. A3 负责让人看懂证据，并管理审核、报告和发布。

一句话总版本：

> ReleaseFoundry 是一个 Agent 质量评测和发布治理平台。它不是只看 Agent 最后说了什么，而是检查 Agent 的完整执行过程、工具调用、评分结果和发布风险。

## 二、这个退款案例是真的吗

演示前必须统一口径：

- 订单 `order_demo_123` 是模拟订单。
- 42 元是模拟金额。
- 固定演示 `refund-demo` 的 Agent 回答来自脱敏教学样本，用于稳定展示失败。
- 动态演示 `live-refund-demo` 会在 Docker 中调用 `qwen2.5:0.5b`，现场生成新 Run 和 Trace。
- 动态 Agent 只可调用 `refund_order_sandbox`，并且输出安全边界会修正“真实退款”等误导性表述。
- 没有连接真实退款系统。
- 不会操作真实资金。
- A1、A2、A3 使用的数据字段、连接方式和页面处理流程是真实项目代码。

老师问时可以直接回答：

> 我们准备了两层演示。第一层是固定失败样本，保证课堂演示稳定；第二层会在 Docker 中运行真实本地模型 Agent，调用内存沙盒退款工具，经过 A1 Trace、A2 Judge 和 A3 Dashboard/Report。模型推理是真实执行的，但订单、金额和工具都是模拟的，不会碰真实资金。

## 四、10 至 12 分钟逐字讲稿

### 0:00 - 0:40 开场

屏幕：先停留在登录页，不要立刻点击。

你可以照着念：

> 大家好，我们做的是 ReleaseFoundry，它是一个面向 Agent 的评测、审核和发布治理平台。普通聊天页面只能看到 Agent 最后的回答，但企业真正关心的是：它执行了什么、有没有正确调用工具、结果有没有证据、失败后能不能被阻止发布。今天我用一笔电商退款案例，演示 A1、A2、A3 怎么形成一条完整证据链。

停顿一下，然后补充：

> 今天使用的是脱敏模拟案例，不涉及真实订单和真实资金。这样做是为了让演示稳定、可重复，也不会产生业务风险。

老师此时应该听懂：你们做的不是普通聊天机器人，而是检查和治理 Agent 的系统。

### 0:40 - 1:30 登录页与产品边界

屏幕操作：用鼠标指向“一键进入退款案例演示”，暂时不要点。

你可以照着念：

> 这是产品登录入口。目前我们已经设计了邮箱注册、Google 和 GitHub 身份入口，以及只读演示入口。为了不伪造生产能力，Google 和 GitHub 首次登录仍明确标记为待接入。今天我们使用只读演示，不创建账号，也不会写入真实审批记录。

指向灰色或禁用的登录入口：

> 禁用状态不是页面坏了，而是系统采用 fail closed，也就是外部身份、权限和审计条件没有完整满足时，宁可不允许操作，也不假装成功。

现在点击“一键进入退款案例演示”。

### 1:30 - 2:50 总览页面

屏幕：进入“发布总览”。

你可以照着念：

> 现在进入 A3 的发布总览。顶部的数据源显示“新手演示，电商退款失败”，说明当前看到的是专门为教学准备的数据。这个案例一共有 1 次运行、1 个案例、0 个通过、1 个失败，平均分是 42。

指向四步新手指引：

> A3 给第一次使用的人安排了四步路径：第一，找到失败案例；第二，查看失败证据；第三，理解人工审核；第四，查看发布阻断。用户不需要先理解所有专业术语，也能按顺序完成检查。

指向黑色发布信号区域：

> 当前页面显示不得发布。这里不是 A3 自己随便决定失败，而是 A3 汇总 A1 的执行证据和 A2 的权威评测结果。如果证据不完整、候选版本不一致或者 A2 判定阻塞，A3 就不能把它包装成通过。

这一段的核心：Dashboard 是总控制台，不是评分器本身。

### 2:50 - 3:50 运行与案例列表

屏幕操作：点击“01 找到失败案例”，进入“运行与案例”。

你可以照着念：

> Run 可以理解为一次完整测试批次。一次 Run 里面可以有很多 Case，也就是很多测试题。这里为了方便教学，只有一个退款 Case。

指向表格的状态、分数和失败分类：

> A3 把 A1 的运行数据和 A2 的评分数据连接在同一行。这里可以看到状态是失败，分数是 42，失败类型是“缺少必需工具调用”。在真实项目中，可以通过搜索、状态和失败类型快速筛选大量案例。

点击表格最右侧箭头进入案例详情。

### 3:50 - 5:20 Expected 与 Actual

屏幕：案例详情页顶部。

你可以照着念：

> 这个场景是：用户要求把订单 `order_demo_123` 退款 42 元。页面首先给出一句最重要的结论：问题不在回答好不好听，而在退款根本没有被执行。

指向 A1、A2、A3 三步说明：

> A1 像黑匣子记录仪，记录执行过程；A2 像阅卷老师，根据 Scenario 规则评分；A3 像质检和发布控制台，把证据展示给审核人员。

指向 Expected：

> Expected 不是单纯的标准答案文字。它表示这个场景要求 Agent 做什么。这里要求先调用 `refund_order`，订单号必须正确，而且只有工具返回成功后，Agent 才能告诉用户退款成功。

指向 Actual：

> Actual 是 Agent 实际做的事。它直接回答“已经完成 42 元退款”，但是没有退款工具的执行结果。所以这句话虽然听起来合理，却没有业务证据支撑。

总结一句：

> Expected 和 Actual 的对比，可以快速发现“说得对，但实际上没做”的 Agent 问题。

### 5:20 - 6:50 Trace 时间线与 Tool Call

屏幕操作：向下滚动到 Trace 时间线和实际工具调用。

你可以照着念：

> Trace 是 Agent 一次运行的完整时间线。我们不只保存最终回答，还记录用户消息、Agent 消息、工具调用和工具返回结果。

依次指向三条 Trace：

> 第一步，用户提出退款请求。第二步，系统检查本应出现的 `refund_order`，但状态是 missing。第三步，Agent 没有获得工具结果就直接回答退款成功。

指向右侧“实际工具调用”：

> Tool Call 是 Agent 对外部能力的实际调用，例如查订单、退款、发邮件或者查询数据库。这里实际调用数量为 0。没有 Tool Call，也没有 Tool Result，所以系统不能证明退款发生过。

老师可能问“为什么不能相信 Agent 的回答”，你立即回答：

> Agent 的文字只能证明它说了什么；工具返回结果才能证明业务系统真的执行了什么。

### 6:50 - 8:10 Judge 判定

屏幕操作：继续向下滚动到 Judge 判定。

你可以照着念：

> Judge 是自动评分器，不是人工审核员。A2 根据 Scenario 中的规则检查 Agent 的执行结果。这里使用的 Judge 叫“退款工具契约”，原始技术 ID 也保留在下面，方便开发人员追踪。

指向 42/100 和失败状态：

> Judge 发现必需的 `refund_order` 没有被调用，因此输出 42 分、FAIL 和 `missing_required_tool`。A3 只消费并展示 A2 的结果，不会偷偷重算，也不会把失败改成通过。

点击“查看评分细项与修复建议”：

> 这里可以进一步看到评分细项。必需工具执行没有通过，最终回答也缺少工具结果支撑。修复建议是重新运行 Agent，并强制它在最终回答前调用退款工具。

解释 Pass/Fail：

> Pass 表示达到场景规则，Fail 表示至少有一项关键要求没有满足。分数用于表示完成程度，但是否能发布还要同时看严重程度、证据完整性和发布策略。

### 8:10 - 9:40 人工审核

屏幕操作：点击左侧“人工审核”。

你可以照着念：

> 自动 Judge 适合批量检查，但企业不能把所有高风险决定完全交给模型。因此系统还需要人工审核层。

依次指向三个步骤：

> 第一步，A2 自动 Judge 产出分数、Pass/Fail 和失败原因。第二步，真人处理高风险案例、业务例外或者多个模型有分歧的情况。第三步，交付门禁综合 A1 证据、A2 判定和人工记录，决定是否允许发布。

指向批准、拒绝和豁免按钮：

> 当前按钮不可点击不是 Bug。真实审批需要登录身份、RBAC 角色权限、数据库持久化和审计记录。这个只读 Demo 可以展示判断流程，但不会伪造一个真人批准结果。

解释 RBAC：

> RBAC 就是按照角色控制权限。例如普通查看者只能看证据，审核员可以提交审核，管理员才能管理成员和策略。

解释 Waiver：

> Waiver 是有条件豁免。它不是把失败改成成功，而是在记录负责人、理由、范围和有效期后，允许一个明确的例外。没有审计记录的豁免不应该生效。

### 9:40 - 10:40 交付门禁

屏幕操作：点击左侧“交付闭环”。

你可以照着念：

> 最后是交付门禁。它回答的不是“Agent 看起来怎么样”，而是“这个候选版本有没有足够证据交给客户”。

指向 BLOCK、integrity invalid 或相关阻断状态：

> 当前候选版本仍然被阻断。只要 A1 执行证据、A2 判定、候选版本绑定或者人工审计有关键缺口，系统就不能输出 production ready。A3 也不能绕过 A2 的权威判定。

强调：

> 这种设计的价值是防止一个页面按钮、人工口头决定或者不完整数据，把失败 Agent 错误发布给客户。

### 10:40 - 11:30 报告与收尾

可选屏幕操作：如果时间充足，点击左侧“报告”。如果时间不足，留在交付页面。

你可以照着念：

> A3 还可以把运行结果、失败案例、Trace、Judge 结论和发布状态整理成报告。后续目标是形成可分享、可撤销、可过期并且带访问审计的 Hosted Report。

最后总结：

> 这条退款案例展示了完整逻辑：用户提出请求，Agent 给出回答，A1 记录执行过程，A2 根据规则评分，A3 展示 Expected 和 Actual 的差异、组织人工审核，并在证据不足时阻止发布。当前案例本身是模拟的，但 A1、A2、A3 的字段连接、页面处理和安全边界是项目真实实现。

结束句：

> 现在我们已经增加了 Docker 本地模型动态演示。每次执行都会生成新的 Run ID、Trace、A2 GradeResult 和 A3 报告，同时继续用沙盒隔离真实资金风险。

## 六、老师常见追问与标准回答

### 1. “这个 Agent 是真的吗？”

> 我们有两个 Agent 案例。固定失败案例是脱敏样本；动态案例是真实运行的 Docker Ollama Agent。动态案例会产生新 Run ID 和真实工具决策，但工具只处理内存中的模拟订单，不连接真实退款系统。

### 2. “为什么还保留固定 Agent？”

> 固定样本用于网络或 Docker 故障时兜底，也方便稳定讲清楚失败证据。动态案例已经使用真实本地模型 Agent；它调用的仍是模拟退款工具，所以不会操作真实资金。

### 3. “42 分是谁打的？”

> 42 分来自 A2 GradeResult。A3 只读取和展示这个结果，不负责改变 A2 的评分语义。

### 4. “A1、A2、A3 为什么要分开？”

> 分开可以避免 Agent 自己执行、自己评分、自己批准。A1 负责事实，A2 负责独立判断，A3 负责人类可见的治理和交付。

### 5. “Scenario 是什么？”

> Scenario 是一套测试题和评分要求。它包含用户输入、期望结果、必需工具、禁止行为和评分规则。

### 6. “Trace 是什么？”

> Trace 是一次运行的时间线，记录消息、工具调用、工具结果和执行状态，类似 Agent 的黑匣子。

### 7. “Tool Call 是什么？”

> Tool Call 是 Agent 对外部系统的实际操作请求。退款、查订单和发邮件都需要通过工具完成，不能只靠文字声明。

### 8. “Expected 是标准答案吗？”

> 不只是标准答案。Expected 还可以规定必须调用什么工具、参数是什么、调用顺序是什么，以及哪些事实不能出现。

### 9. “人工审核为什么有必要？”

> 自动评测适合大规模筛查，但高风险操作、业务例外和模型分歧需要真人承担治理责任，并留下可审计记录。

### 10. “为什么审批按钮不能点？”

> 真实审批必须有可信登录身份、角色权限、数据库记录和审计回执。条件不足时系统保持只读，避免伪造审批。

### 11. “Waiver 是不是绕过失败？”

> 不是。Waiver 是有负责人、理由、范围和有效期的受控例外，而且必须被审计。它不能修改原始 A2 评分。

### 12. “这个系统现在能直接商用吗？”

> 还不能直接宣称生产可用。学生 MVP 已经具备运行证据、评测展示、人工审核界面、报告和发布门禁的产品形态，但真实身份、生产数据库、企业部署和完整审计仍需闭环。

### 13. “你负责的 A3 做了什么？”

> 我负责把 A1 的 Run、Trace、Tool Call 和 A2 的 Score、Pass/Fail、Failure Class 接到 Dashboard，完成案例详情、失败分析、人工审核、报告、团队管理和发布治理界面。

### 14. “为什么说 A2 是权威评分方？”

> 因为 A3 不应该为了让页面显示通过而重新计算或修改评分。A2 的 Judge 和 Decision Ledger 是评测权威，A3 只消费结果并执行治理边界。

### 15. “真实版本怎么升级？”

> 本地模型、沙盒工具、新 Trace、同一 Run ID 的 A2 评分和 A3 API 导入已经完成。下一步是持久化数据库、托管身份和经过授权的真实业务集成；在获得权限和审计能力前不会连接真实付款系统。

## 七、现场容易说错的话

不要说：

> 我们已经接通真实退款系统。

应该说：

> 我们完成了脱敏退款教学案例和 A1/A2/A3 数据闭环。

不要说：

> A3 给 Agent 打了 42 分。

应该说：

> A2 输出 42 分，A3 读取并展示 A2 的权威结果。

不要说：

> 人工审批已经可以正式使用。

应该说：

> 人工审核界面和安全边界已经完成，真实写入仍需要身份、权限和持久审计后端。

不要说：

> 当前已经 production ready。

应该说：

> 当前系统会在证据不完整时正确阻断，生产部署和企业回执仍是后续工作。

不要说：

> Trace 就是聊天记录。

应该说：

> 聊天消息只是 Trace 的一部分，Trace 还包含工具调用、工具结果、执行状态和时间顺序。
