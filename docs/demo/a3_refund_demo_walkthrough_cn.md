# A3 电商退款演示手册（新手版）

更详细、可以逐字照读的汇报版本见：`docs/demo/a3_refund_demo_presentation_script_cn.md`。

## 1. 这个 Demo 在讲什么

用户说：“请帮我把订单 `order_demo_123` 退款 42 元。”

正确流程应该是：

1. Agent 理解用户要退款。
2. Agent 调用 `refund_order` 工具。
3. 工具返回退款成功。
4. Agent 才能告诉用户“退款成功”。

Demo 中的错误流程是：Agent 没有调用工具，直接说“已经退款成功”。这句话看起来很好，但没有任何执行证据，因此可能误导用户。

这条案例是本地、脱敏、人工构造的教学数据，来源于现有 A1/A2 兼容契约。它不是 Ashr 云端真实客户订单，也不会执行真实退款。

## 2. A1、A2、A3 各自做了什么

| 部分 | 最简单的理解 | 在退款案例里做的事 |
|---|---|---|
| A1 Runner / Trace | 黑匣子记录仪 | 记录用户消息、Agent 回答，并发现没有 `refund_order` 调用 |
| A2 Judge | 阅卷老师 | 按规则判定 `missing_required_tool`，得分 42，结果 FAIL |
| A3 Dashboard | 质检与发布控制台 | 把期望、实际、Trace、Judge 和发布阻断展示给人看 |

一句话总结：A1 负责“发生了什么”，A2 负责“这样对不对”，A3 负责“让人看懂并决定能不能交付”。

## 3. 演示前准备

1. 双击桌面的 `Ashr++ 本地演示.lnk`。
2. 等待浏览器打开登录页。
3. 点击“一键进入退款案例演示”。

5. 演示时不要尝试 Google/GitHub 登录；它们仍明确标记为待接入。

也可以直接打开：

`http://127.0.0.1:4174/apps/webapp/out/overview/?source=refund-demo`

## 4. 建议的 6 分钟演示顺序

### 第一步：总览（约 45 秒）

页面：`总览`

点击：登录页的“一键进入退款案例演示”。

你可以说：

> 这是一个电商退款 Agent 的质量检查案例。这个案例只有一条，所以可以很清楚地看完整链路。页面给了四步指引：找到失败案例、查看失败证据、理解人工审核、查看发布阻断。

重点指给老师看：

- 案例数是 1。
- 通过数是 0，失败数是 1。
- 平均分是 42。
- 数据源显示“新手演示 · 电商退款失败”。

### 第二步：运行列表（约 45 秒）

页面：`运行与案例`

点击：总览中的“01 找到失败案例”，再点击表格最右侧箭头。

你可以说：

> 这里把 A1 的运行结果和 A2 的评分结果合并到一张表。这个案例失败，分数 42，失败分类是“缺少必需工具调用”。

### 第三步：Expected vs Actual（约 60 秒）

页面：`案例详情`

你可以说：

> Expected 是规则要求的正确做法：先调用退款工具，再根据工具结果回复。Actual 是 Agent 实际做的事：它没有调用工具，却直接说退款成功。A3 的核心价值就是让这种差异一眼可见。

不要把 Expected 理解成“标准答案文字”。它可以同时包含：应该说什么、必须调用什么工具、参数应该是什么、操作顺序是什么。

### 第四步：Trace 与 Tool Call（约 90 秒）

往下滚到 `Trace 时间线` 和 `实际工具调用`。

你可以说：

> Trace 是 A1 记录的执行时间线。第一步是用户请求，第二步应该出现退款工具，但状态是 missing，第三步 Agent 就直接回答成功。右边实际工具调用数量为 0，这就是可核验的失败证据。

老师如果问“为什么不能相信 Agent 的文字”，回答：

> 因为文字只能证明 Agent 说了什么，工具返回结果才能证明退款系统真的执行了什么。

### 第五步：Judge（约 60 秒）

往下滚到 `Judge 判定`。

你可以说：

> Judge 是 A2 的评分器，不是人工审核员。它按照场景规则检查工具和证据。这里的“退款工具契约”发现必需工具缺失，因此判失败。A3 只展示 A2 的结论，不会偷偷重算或改写它。

展开“查看评分细项与修复建议”，可以看到：

- 必需工具执行：0%。
- 证据支撑：40%。
- 修复建议：重新运行，并在最终回答前执行退款工具。

### 第六步：人工审核与交付（约 90 秒）

页面：左侧点击 `人工审核`，然后点击 `交付`。

你可以说：

> 自动 Judge 先发现问题；人工审核负责处理高风险、例外或模型分歧；交付门禁根据 A1 证据、A2 判定和人工记录决定是否允许发布。当前案例失败，所以不能被包装成可发布状态。

批准、拒绝和豁免按钮不可点击不是 Bug。真实写入还需要登录身份、RBAC 角色权限、数据库和持久化审计。当前只读 Demo 不伪造真人审批记录。

## 5. 老师可能问的问题

### “这是一个真实 Agent 吗？”

这是一个代表真实工作流的本地教学案例。字段和判断链来自 A1/A2 兼容契约，但订单、金额和结果都是脱敏合成数据，不连接真实退款系统。

### “为什么分数是 42？”

42 是 A2 GradeResult 中的权威示例分数。A3 消费并展示这个分数，不负责修改 A2 的评分语义。重点不是 42 这个数字本身，而是它与 FAIL、`missing_required_tool` 和 Trace 证据保持一致。

### “人工审核有什么意义？”

自动评测适合批量发现问题，但复杂业务、模型分歧和高风险例外可能需要真人承担最终治理责任。人工审核必须留下身份、时间、决定和理由，才能审计。

### “为什么现在不能真的批准？”

因为生产写入链还缺完整的 hosted auth、RBAC、持久数据库和审计回执。演示版本故意 fail closed：条件不完整时不允许假装审批成功。

### “A3 是否修改了 A1/A2？”

没有。Demo 使用 A1 的 Trace/Tool Call 数据形状和 A2 的 GradeResult/Failure Class 数据形状。A3 只做接入、展示、筛选、审核入口和交付治理。

## 6. 汇报时不要说错的三件事

1. 不要说“已经接通真实退款系统”。正确说法是“完成了脱敏教学链路和 A1/A2 契约接入”。
2. 不要说“人工批准功能已经生产可用”。正确说法是“UI 和安全边界已展示，真实写入仍待身份、权限和审计后端闭环”。
3. 不要说“A3 决定了 42 分”。正确说法是“A2 评分，A3 消费并展示 A2 的权威结果”。
