# A1 Worker DB Migrator

`services/api/db_migrator.py` is the executable layer below the canonical data model in `services/api/data_model.py`.

## Scope

- Uses only Python standard-library `sqlite3`, `hashlib`, `json`, and dataclasses.
- Reads no environment keys or secret material.
- Does not depend on `recon/`, `tools/`, or `private_refs/`.
- Executes only SQLite plans locally; Postgres output is deterministic SQL text for production review/apply tooling.

## Capabilities

- `generate_migration_plan(dialect="sqlite")` translates `TABLES` into deterministic sqlite-compatible DDL steps.
- `generate_migration_plan(dialect="postgres")` emits Postgres-compatible DDL using `TIMESTAMPTZ`, `JSONB`, quoted identifiers, partial indexes, and `CREATE ... IF NOT EXISTS` guards.
- Every `MigrationPlan` carries a SHA-256 `checksum` over the schema contract and rendered DDL, so downstream apply tooling can detect drift.
- `MigrationPlan.ledger_sql_script()` emits `schema_migrations` DDL plus an idempotent schema-version/checksum upsert for the selected dialect.
- `MigrationPlan.rollback_sql_script()` emits best-effort rollback text for empty or unapplied deployments: delete the ledger entry, drop indexes, then drop tables. Postgres table drops include `CASCADE` because the canonical model may gain FK enforcement later.
- `build_ledger_entry()`, `validate_schema_ledger()`, and `validate_sqlite_drift()` provide checksum/version drift validation primitives.
- `validate_tenant_indexes()` validates that each tenant-scoped table/index preserves the `tenant_id` leading-key contract.
- `apply_migration_plan()` applies SQLite plans to a supplied sqlite connection or a new in-memory connection. Pass `record_ledger=True` to create/update the local `schema_migrations` ledger.
- `apply_to_memory_and_introspect()` applies the generated SQLite plan to sqlite `:memory:` and returns table/index names.
- `introspect_sqlite()` returns non-internal table and index names from `sqlite_schema`.

## Operational Notes

Postgres plan generation is intentionally stdlib-only and side-effect-free. A production deployer should run the generated SQL inside its own transaction/error handling path, then persist the matching ledger row from `ledger_sql_script()`. Before applying a new version, compare the live ledger row with `validate_schema_ledger()` or equivalent database-backed logic and fail closed on checksum mismatch.

The rollback text is a planning primitive, not a data-preserving rollback engine. It is safe to review for a failed fresh install or ephemeral environment, but production rollback needs backups or forward migrations when data exists.

## Relationship to Existing Docs

The existing `worker_data_model.migration.sqlish` file remains the SQL-ish documentation contract generated by `export_sqlish_migration()`. The migrator is intentionally separate so adapters can test a real sqlite execution path and generate Postgres-compatible production SQL without changing the DB-shaped schema docs.
